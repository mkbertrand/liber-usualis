#+TITLE: Liber Usualis - Architecture
#+AUTHOR: David Villafana
#+OPTIONS: toc:3

* Overview

  Liber Usualis is a data-driven liturgical text generation system for the Roman
  Catholic Divine Office. Given a date and an occasion, it selects the governing
  liturgical tag sets, composes tagged content, superimposes translations, chant,
  and section headers, and renders the result to HTML on the server. The currently
  supplied Roman Breviary data follows the 1888 edition.

  Tags are the central domain model. Liturgical choices should normally be
  represented by tagged content, category files, discrimination tables, annual
  and daily rule tables, or implication rules rather than feast-specific branches
  in Python or JavaScript.

** Technology Stack

   | Layer          | Technology                                                    |
   |----------------+---------------------------------------------------------------|
   | Backend        | Python 3.13, Bottle, Waitress                                 |
   | Frontend       | @preact/signals-core, Exsurge.js, Temporal polyfill, esbuild  |
   | Templates      | Bottle templates                                              |
   | Data           | Tagged JSON plus untagged text and GABC resources             |
   | Infrastructure | Nix flakes and native nixpkgs image builders                  |

* Backend

** Module Boundaries

   The request-to-content flow is divided across the following modules:

   - =server.py= parses HTTP parameters, invokes domain operations, and serializes
     responses.
   - Root =datamanage.py= constructs the configured corpora and orchestrates rite
     requests, office selection, translation, chant, headers, and rendering. Its
     request functions are memoized with =functools.lru_cache=.
   - =kalendar/kalendar.py= constructs and prioritizes the annual kalendar.
   - =kalendar/daily_tagger.py= applies diurnal, Vesperal, Martyrology, votive, and
     implication rules for a particular date.
   - =kalendar/datamanage.py= loads kalendar data and caches annual results.
   - =kalendar/display.py= builds the display kalendar served to the kalendar page.
   - =composer/book.py= loads one book's tagged, category, discrimination, and
     untagged resources.
   - =composer/corpus.py= searches across books and recursively composes rites.
   - =composer/rite.py= superimposes contingent content onto a composed rite.
   - =composer/psalms.py= resolves psalm references in untagged files.
   - =renderer/= renders a composed and superimposed rite to HTML (see Stage 5).
   - =version_management.py= resolves the request's locales, finds the best
     localized resource file, and appends content hashes to resource URLs.
   - Root =breviarium.py= is a CLI and test-facing consumer of this pipeline. It is
     not the composition engine.

   The =Bookshelf= boundary in =bookshelf/bookshelf.py= exposes =book_srcs()= to
   kalendar code. Both =Corpus= and the kalendar's lightweight =KalendarCorpus=
   satisfy that interface, so =kalendar/= does not depend on =composer/=.

   One documented exception to keeping domain calls out of the presentation layer:
   =web/templates/pray.tpl= calls =datamanage.rendered_rite_request()= and
   =datamanage.rite_request()= directly to render the first rite, its day title,
   and the next-hour link server-side. Both calls hit the same memoized results as
   =/api/rite=.

** HTTP API: =server.py=

*** Pages

    - =GET /= redirects to =/index=; =GET /<page>= redirects to the same page in the
      best locale from =Accept-Language= (=version_management.localehunt()=),
      falling back to English.
    - =GET /<locale>/<page>= renders a top-level page (=index=, =de-anno=,
      =kalendar=, =rubricae=, =pray=, =about=, =credit=, =donate=, =help=,
      =resources=). =index= uses =web/templates/menu.tpl=; =de-anno=, =kalendar=,
      and =rubricae= use =latin-generic.tpl=; =pray= uses =pray.tpl=; the rest use
      =generic.tpl=. A bare =/<locale>/pray= renders the pray page with no rite;
      the client then chooses the most relevant one and navigates to it.
    - =GET /<locale>/<officium|ritus>/<date>/<occasion>= and
      =GET /<locale>/<officium|ritus>/<date>/<select>/<occasion>= render a rite
      page. =select= is =officium-parvum-bmv= or =officium-defunctorum= (the primary
      office when omitted); the =v= query parameter carries plus-separated votive
      tags; the =opt= cookie carries option tags. The locale chooses the
      translation (=en= English, =de= German, =nl= Dutch, otherwise none).

*** =GET /api/rite=

    Returns a rendered rite as HTML for in-page navigation. Parameters:

    - =loc= - page locale, mapped to the translation as for rite pages
    - =date= - ISO date, =YYYY-MM-DD=
    - =occasion= - the occasion and prayer type, e.g. =matutinum-laudes+officium=
    - =s= - the selected office, default =primarium=
    - =v= - plus-separated votive tags

    Option tags come from the =opt= cookie. The route calls
    =datamanage.rendered_rite_request()=.

*** =GET /api/ordo=

    Parameters:

    - =date= - ISO date, =YYYY-MM-DD=
    - =time= - =vesperale= or =diurnale=
    - =votives= - plus-separated enabled votive tags; an empty value is allowed

    =datamanage.ordo()= calls =daily_tagger.get_vespers()= or
    =daily_tagger.get_diurnal()= and returns:

    - =tags= - all resolved tag sets
    - =primary= - the primary name and tag set
    - =commemorations= - ranked name/tag-set pairs
    - =omissions= - ranked omitted name/tag-set pairs
    - =commemoratio-matutini= - the Matins commemoration, when present
    - =psalmi= - vesperal only: the office whose psalms are said, when the vesperal
      rules take them from an office other than the primary one; otherwise null

*** Other Endpoints

    - =GET /api/composer= returns the composed, superimposed rite as JSON before
      rendering (=datamanage.rite_request()=: =text=, =used-primary=,
      =used-commemorations=, =commemoratio-matutini=). Its parameters are =date=,
      =rite=, =opt=, =select=, =translation=, and =votives=.
    - =GET /api/kalendar= returns the navigation skeleton and display kalendar.
    - =GET /resources/<path>= serves frontend resources.
    - =GET /favicon.ico=, =GET /robots.txt=, and =GET /logs/internal_requests=
      serve static files.

** Stage 0: Books and Corpora

   Repository-managed books live directly under =data/=. Externally maintained
   books are synchronized into =data/generated/=. The flake pins
   =liber-usualis-chant= and the =databased= branch of
   =franciscan-chant-closet= and installs their files into
   =data/generated/liber-usualis-chant= and =data/generated/fcc= in both the
   development shell and production. Matching files are replaced while unrelated
   generated content is preserved. =sync-books.py= remains available for non-Nix
   checkouts using an optional repository-root =books.json=. The generated path
   and operator configuration are ignored by Git.

   A =Book= identifies a source directory and a book-title tag. A =Corpus= searches
   one or more primary books. A =ContingentCorpus= retains the primary-book context
   while searching separate content books, which is how translations and chant are
   applied without changing the structure of the Latin rite.

   Root =datamanage.py= currently constructs:

   - =DEFAULT_CORPUS= from the 1888 breviary and 1846 Martyrology
   - =ENGLISH_CORPUS=, =DEUTSCH_CORPUS=, and =NEDERLANDS_CORPUS= from translation
     books
   - =CHANT_CORPUS= from the generated chant books (=liber-usualis-chant=, its
     =nocturnale=, and =fcc=)
   - =HEADER_CORPUS=, a =CaputCorpus= over =DEFAULT_CORPUS='s own books, for section headers

** Stages 1 and 2: Kalendar and Daily Tagging

*** Annual Kalendar

    =kalendar/kalendar.py= assembles each book's kalendar sources into their normal
    dates, applies the annual =tabella.json= rules, resolves precedence and
    translations of feasts, and caches the completed year through
    =kalendar/datamanage.py=.

    Annual rule processing and daily rule processing are separate responsibilities.
    The annual engine must remain usable through the =Bookshelf= interface rather
    than importing composer classes.

*** Daily Tagging

    Daily rule tables live in =data/{book}/kalendarium/=:

    - =tabella-diurnalis.json= controls the daytime office.
    - =tabella-vesperalis.json= resolves first and second Vespers.
    - =tabella-diurnalis-votivarum.json= and =tabella-vesperalis-votivarum.json=
      are applied first, and only when votives are requested.
    - =tabella-martyrologii.json= controls the Martyrology reading.
    - =sequentes.json= adds implied tags.

    Rules use =include= and =exclude= restrictions and declarative operations such
    as =crea=, =combina=, =mutate=, =duplicate=, =dele=, and =errora=.

    =get_vespers(bookshelf, day, votives)= resolves the overlap between the current
    day's second Vespers and the next day's first Vespers. =get_diurnal(bookshelf,
    day, votives)= applies daytime and Martyrology rules, including the next day's
    lunar tag for Martyrology. Each requested votive office is first made primary
    (=primarium=, =semiduplex=) by a generated rule, before the votive tables. After
    the rules, =sequentes.json= implications are added to every tag set. The output
    is a sequence of service tag sets describing the primary office,
    commemorations, omissions, and applicable votives.

** Stage 3: Composition

*** Loading Tagged Content

    =Book.get_tagged_file()= loads JSON entries from a book's =tagged/= tree and
    adds the book title to every tag set. The normal entry shape is:

    #+BEGIN_SRC json
    {
      "tags": ["immaculata-conceptio-bmv", "nomen"],
      "datum": "Immaculatae Conceptionis B.M.V."
    }
    #+END_SRC

    =tags= may also be a list of tag lists when the same datum belongs to multiple
    contexts. Any key other than =tags= and =datum= is expanded into a separate
    entry whose tags include that key. This supports compact structured source data
    without treating extra keys as arbitrary metadata.

    Chant is not fetched from =src= values in primary data. It is tagged content in
    a contingent corpus and is attached during superimposition.

*** Recursive Composition

    =Corpus.compose(item, selected, alternates)= is the public composition entry
    point and returns a =Rite=. It delegates recursion to =Corpus._process()=:

    1. A set of tags is a search request.
    2. Contradicted positional tags are removed from the selected context.
    3. An explicit =occurrens= reference or a matching alternate can switch the
       active feast context.
    4. Requested temporal tags replace contradicted temporal context.
    5. =Corpus.search()= resolves the resulting query.
    6. Lists under =datum= are recursively composed; strings are returned as text,
       with saint-name substitution where required.

    A query containing =commemorationes= is handled by
    =Corpus.handlecommemorations()=: one =formula-commemorationis= is composed per
    ranked commemoration and a shared terminating collect is appended.

*** Search and Discrimination

    =Corpus.search(query)= resolves content as follows:

    1. A tag beginning with =/= is treated as an untagged-resource reference. The
       primary =Corpus= resolves these through =composer/psalms.py=;
       =ContingentCorpus= recognizes =/psalmi= references and otherwise retrieves a
       matching untagged resource from its content books.
    2. The corpus builds a pile from files named by the query plus the default pile
       names (=DEFAULT_PILE=), across all primary books.
    3. Book-title tags are added to the query.
    4. Entries whose tags are subsets of the query become candidates.
    5. Rules from =discrimina/general.json= are applied in order. Whenever at least
       one candidate matches a rule, nonmatching candidates are discarded.
    6. A sole candidate is returned immediately. Otherwise candidates are ordered
       by tag count; a uniquely more specific candidate wins, and a remaining tie
       raises an ambiguity error unless the caller explicitly requested multiple
       results.

    =Corpus.discriminate(table, tags)= is a separate bitmask ranking operation used
    where complete tag sets, such as commemorations, must be sorted (for example
    with =discrimina/rank.json=). It is not the candidate-filtering implementation
    used by =Corpus.search()=.

*** Untagged Resources and Psalms

    Untagged resources live under each book's =untagged/= tree and may be JSON,
    text, or GABC. =Book.retrieve_untagged_file()= verifies that resolved paths stay
    inside that tree. Psalm references such as =/psalmi/psalmus-i= are interpreted
    by =composer/psalms.py=, which extracts the requested portion of the untagged
    psalm text.

** Stage 4: Superimposition

   =Rite.superimpose(corpus, tag)= deep-copies the composed rite and traverses its
   tagged nodes. It searches the supplied =ContingentCorpus= using each node's
   =quaesitum= or tags and attaches matching content under =tag=. Root
   =datamanage.rite_request()= uses this operation to attach translations under
   =translation=, chant under =cantus=, and section headers under =caput=,
   returning a new =Rite= each time.

   Translation books remain parallel to source content through matching query tags:

   - =data/breviarium-1888-english/=
   - =data/breviarium-1888-deutsch/=
   - =data/breviarium-1888-nederlands/=

   Generated chant books live under =data/generated/=. The renderer receives
   translated and chanted content inline in the rite tree; it does not perform a
   second translation lookup.

*** Section Headers

    Section headers (e.g. "Ad Matutinum.", "Nocturnus I.") are superimposed under
    =caput= from =HEADER_CORPUS=, a =CaputCorpus= (=composer/corpus.py=) rather
    than being computed by the renderer or composed into =datum=. =CaputCorpus=
    searches the same books and files as =DEFAULT_CORPUS=, filtered to entries
    tagged =caput=: an entry's =caput= key (e.g. =\"caput\": \"Ad Matutinum.\"=)
    expands, via =Book.get_tagged_file()='s normal key-expansion, into a
    standalone entry tagged with the entry's own tags plus =caput=, living
    alongside the body content it heads without being referenced from any
    =datum= list. =CaputCorpus.search()= never resolves untagged (=/=-prefixed)
    references, so only genuine tagged header entries are ever candidates.

    An entry's render level -- the default centered =item-header=, the larger
    =section-header= (=sectio=), or an inline heading annotation (=annotatio=)
    -- is carried as an additional tag on the entry itself. =CaputCorpus.LEVELS=
    (=caput=, =sectio=, =annotatio=) is injected into every query
    unconditionally, mirroring how =Corpus.search()= always adds book tags, so
    an entry can require one of the level tags without that tag ever needing to
    already exist in a node's real liturgical context.

    Each =caput= entry lives alongside the specific content it heads: e.g. the
    Invitatorium and Te Deum headers sit next to their entries in
    =psalterium/matutinum.json=, and the four Responsory/Lectio-absolution
    headers sit in =psalterium/absolutiones-benedictiones.json= next to the
    absolutions themselves. A header tied to no single hour (Psalmi., Collecta.,
    the default Hymnus., Responsorium Breve.) lives in the book-wide
    =tagged/formulae.json=, which =DEFAULT_PILE= (=composer/corpus.py=) already
    includes in every search regardless of query.

    Because =Rite.superimpose()= tests every node's own accumulated =quaesitum=
    (or =tags=) independently, a =caput= entry's tags must uniquely identify one
    node to avoid attaching the same header throughout a whole subtree. This
    normally falls out of the existing =positionales= contradiction handling:
    e.g. bare =ritus= and bare =nocturna= are stripped from =selected= as soon as
    composition descends past the office or nocturn boundary (both are grouped
    with =responsorium= in =categoriae/positionales.json=), so a =caput= entry
    keyed on, say, =matutinum+ritus= or =nocturna+nocturna-i= matches only that
    one boundary node. Where a header's own content recurses into a nested
    occurrence of the same tags (e.g. the Gloria Patri repeat inside a
    "cum-gloria" responsory, which inherits =responsorium=/=formula= via
    =quaesitum= without carrying them as its own tags),
    =RiteRenderer.do_headering()= (=renderer/rite_renderer.py=) additionally
    requires that at least one of the matched =caput= entry's own tags is also
    uniquely the target element's own tag (via =uniquelyhas()=), so only the
    header's true origin renders it.

    Headers that depend on the *absence* of context (e.g. "not within a
    commemoration", "not the repeated antiphon") are expressed as a second,
    more specific =caput= entry whose =caput= value is =null=, rather than as
    negative conditions in renderer code: subset-matching tag search can express
    "when this extra tag IS present, override the default," never "unless it is
    present," so the override entry's specificity (one more tag than the
    default) is what suppresses the header, and =do_headering()= renders nothing
    when the resolved =caput= is =null=. Empty strings are not used to mean
    "absent"; new data should use =null=. For example, the default =versiculus=
    header (=tagged/formulae.json=) is overridden by a null entry requiring
    =commemoratio= too, and the default Magnificat canticle name
    (=psalterium/vesperae.json=) is overridden by null entries requiring
    =repetita= or =commemoratio=. Note that a commemoration's own ancestor tag
    (=commemorationes=, from =Corpus.handlecommemorations()=) is deliberately
    stripped from =selected= before composing the commemoration's content, so
    it never reaches a descendant's =quaesitum=; the tag that actually appears
    there, and that these override entries key on, is =commemoratio=
    (singular), part of the literal request each commemorated item is composed
    with (see =formula-commemorationis= entries in =tagged/formulae.json=).

    Two entries can also compete on equal footing when neither is a subset of
    the other's requirements (e.g. the default =versiculus= annotation versus
    the item-header used specifically in the Office of the Dead or Holy Week),
    where tag-count specificity alone cannot break the tie and =Corpus.search()=
    would raise rather than guess. In practice this is already resolved by
    =discrimina/general.json= itself -- an existing standalone
    =[\"officium-defunctorum\"]= rule, and an existing =[\"/proprium-de-tempore\"]=
    category rule that covers =coena-domini=/=parasceve=/=sabbatum-sanctum= as
    members of that category -- so no =caput=-specific discrimina rules were
    needed. Confirming this requires searching with the real composed
    =quaesitum= (which includes the full day's temporale/rank/season context)
    against the full discrimina table, not a hand-built query containing only
    the tags that seem relevant: an artificially thin query can under-populate
    the candidate pile (via =Book.get_pile()='s filename-based inclusion) and
    make working disambiguation look broken, or make broken disambiguation look
    like it degrades safely instead of raising.

** Stage 5: Rendering: =renderer/=

   =datamanage.rendered_rite_request()= passes the result of =rite_request()= to
   =renderer.render_rite(date, rite, resources)=, which returns the page's rite
   HTML: a date header, the title of the office used, and the rendered body.
   =RiteRenderer= (=renderer/rite_renderer.py=) walks the rite tree with the tags
   accumulated from its ancestors and decides each node's layout from its own
   tags (the element lists at the top of the module, and handlers for hymns,
   responsories, chant, psalms, lessons, commemorations, the Martyrology, and the
   invitatory). Latin and translation
   are emitted as parallel columns of one =rite-text-container=; the frontend
   rearranges them for line-by-line display.

   - =renderer/rendering_utils.py= holds the shared text transformations (rubric
     and text markup, abbreviation, the date header and titles) and the helpers
     for reading a node's datum and its superimposed content (=unpack()=,
     =unpack_superimposed()=).
   - =renderer/psalmify.py= formats psalm text, pointing it to its psalm tone when
     chant is available.
   - =renderer/chomp.py= prepares a chant's GABC for display. Chanted items are
     emitted as =<gabc-chant>= elements carrying the GABC and translation as
     attributes, with the plain text as a fallback; the browser draws the score.
   - =renderer/hyphenate.py= and =renderer/la_hypher.py= hyphenate Latin with the
     project's tuned patterns.

   The chant resources the renderer needs (invitatory tones and psalm tones from
   the generated chant book) are read on first use by =datamanage.render_resources()=,
   so importing =datamanage= does not require the generated books to be present.

* Frontend

** Page Shell and State: =web/templates/pray.tpl=

   The Bottle template renders the page shell, the first rite server-side, and
   working fallback =href=s for every link, then loads the deferred
   =web/resources/dist/pray.js= bundle (after the Temporal polyfill). Localized
   strings the script needs are written into a =pray-script-text= JSON block. Its
   state is held in =@preact/signals-core= signals:

   - =frontend/pray-store.js= (=makePrayStore()=) owns rite and routing state:
     =displayPath= (path and query string, moved as soon as a navigation starts),
     =ritePath= (the rite whose text is on the page, moved together with =rite=
     once it loads; the next-hour button and marking an hour prayed follow it),
     =riteNavigationType= (the navigation type of that rite, moved with it, or at
     once by =setNavigationType()=; the next-hour button is always forbidden in
     hard navigation),
     =rite=, the =opt= cookie tags,
     =navigationType=, the last completed cursus hour, and =now=. Derived values
     (=contentParams=, and =nextHourButton= built by the pure =nextHourTarget()=) are =computed=
     signals. Its actions (=navigateRite=, =returnToCurrent=, =toggleVotive=,
     =setDesired=, =togglePriest=, =markHourAsDone=, =setNavigationType=, =init=,
     =handlePopstate=) perform the history, cookie, storage, and =/api/rite= side
     effects; =init()= sends a bare =/pray= visit to the most relevant rite
     (=bestHour()=).
     =/api/rite= responses are kept by date and occasion for the current context
     (locale, select, votives, and the =opt= cookie) and discarded when it changes;
     the server-rendered rite is the first entry, and pointing at a rite link
     prefetches its rite through =prefetchRite()=.
     =now= changes only through =updateNow()=. In soft navigation =pray.js=
     schedules it for the next moment what may be said can change (midnight and
     14:00, from =nextCanSayChange()=), and shows the outdated-content banner
     when the displayed rite stops being sayable; hard navigation schedules
     nothing.
   - =frontend/pray-display.js= (=makeDisplayStore()=) owns display-only state:
     the persisted display toggles (stored under a legacy =_x_=-prefixed
     =localStorage= key) and which panels and menus are open.
   - =frontend/pray-ordo.js= defines =OrdoModel= (=createModel=), the ordo panel's
     browsing state: a date and votives that start from the page's rite, and the
     =/api/ordo= responses for that date's diurnal and vesperal offices. =pray-view.js=
     creates one, with the panel's bindings, each time the panel opens and disposes it
     when it closes, so browsing never changes the page until a rite link is followed.
   - =frontend/routing.js= holds pure path functions: parsing a rite path into
     content parameters, building paths, cursus order, and suggested occasion.
   - =frontend/pray-view.js= (=bindPrayPage()=) binds the server-rendered markup
     to both stores. Each binding is an =effect= (state to DOM) or an event
     listener (DOM to state), found by element id or data attribute. It also
     rearranges the rite's parallel columns for line-by-line display
     (=lineByLine()=). Links marked =data-rite-link= navigate in-page and keep the
     current navigation type: hard keeps the chosen rite on reload, while soft lets
     a reload move on to a more relevant rite. A link may name a type with
     =data-rite-link="hard"= or ="soft"=; links followed from the ordo panel are
     hard. =frontend/dom-bindings.js= provides the generic show/hide, focus-trap,
     outside-click, and positioning helpers.
   - On narrow screens (below the compact top bar's 1140px breakpoint) the second
     bar moves to the bottom and shows an hour picker in place of its row of hours.
     The picker's sheet holds the day's hours, the anticipated Matins, "Return to
     current", and the other rites; it reuses the same bindings, which cover every
     copy of these controls, and =web/resources/pray/rite-links.tpl= supplies the
     rite links to both the rites menu and the sheet.

** Chant and Styles

   =frontend/gabc-chant.js= defines the =<gabc-chant>= element, which renders its
   GABC lazily with Exsurge, sharing one configured Exsurge context
   (=frontend/chant-context.js= binds each score to it). When chant
   display and the =play-chant= option are both enabled, tapping a rendered score
   plays it through =frontend/chant-player.js=, a Web Audio sequencer over the
   Exsurge note list. Horizontal drag seeks the playhead to the nearest note;
   vertical swipe still scrolls the page. Playback is presentation-only.

   The frontend sources are bundled from =frontend/pray.js= into
   =web/resources/dist/pray.js=; pray-page styles are bundled from
   =frontend/css/pray/pray.css= into =web/resources/dist/pray.css=. Site-wide
   styles (fonts, theme variables, top bar, shared components) are bundled from
   =frontend/css/style/style.css= into =web/resources/dist/style.css=. Unbundled
   per-page styles live in =web/resources/styles/=, and
   =web/resources/pray/css/pray-mobile.css= is added for mobile user agents.

** Theme, Localization, and Other Pages

   =web/resources/themer.tpl=, included in every template's =<head>=, applies the
   stored or system theme as =data-theme= before the page is drawn and handles
   clicks on the top bar's =#dark-mode-toggle=; CSS shows the matching icon. The
   shared top bar (=web/resources/top-bar.tpl=) includes the locale selector
   (=web/resources/locale-selector.tpl=), which reopens the same path in the chosen
   locale.

   Interface text lives in =web/locales/{locale}/= (=pages/= for each page,
   =resources/= for shared pieces); =version_management.bestlocalized()= falls
   back through the request's locales when a file is missing. Page bodies live in
   =web/pages/=. Other pages are server-rendered Bottle templates; the kalendar
   page builds its table from =/api/kalendar= with
   =web/resources/js/kalendargen.js=.

* Tagging System

** Categories

   Tags are lowercase, hyphen-separated strings. Category definitions live in
   =data/{book}/categoriae/=, including:

   - =positionales.json= defines mutually exclusive positions and contexts.
   - =temporale.json= defines seasons, ranks, propers, and commons, drawing on
     =proprium-de-tempore.json=, =commune-sanctorum.json=, and =gradus.json=.
   - =proprium-sanctorum.json= identifies feasts of saints.
   - =objecta.json= identifies content types.
   - =votiva.json= and =legitur-mense.json= group votive offices and the months
     in which content is read.

   Category entries beginning with =/= reference another category and are expanded
   recursively by =Corpus.expand_cat()=. Queries must not silently retain mutually
   exclusive tags from category groups.

** Runtime Tag Flow

   1. Annual kalendar lookup produces the base occasions for the date.
   2. Daily tables resolve the primary office, commemorations, omissions, and
      votives.
   3. =sequentes.json= adds implied tags.
   4. =datamanage.rite_request()= then applies a small explicit set of request
      adjustments: it adds the Office of the Dead as an omitted office when the day
      has none, un-omits the Little Office for the =cum-opbmv= option, adds the
      =opt= tags to every tag set, and takes the office named by =select= as the
      primary. This is an acknowledged hard-coded boundary and should not be
      expanded when data rules can express the behavior.
   5. Composer combines the selected context with item tags and searches by subset.

* End-to-End Example

  A normal frontend request for Matins follows this sequence:

  #+BEGIN_EXAMPLE
  1. A rite link calls navigateRite() in frontend/pray-store.js, which pushes the
     URL and requests /api/rite?loc=...&date=...&s=...&occasion=matutinum-laudes+officium&v=...
     (unless the rite is already cached, e.g. prefetched on hover).
  2. server.py maps the locale to a translation and reads the opt cookie.
  3. datamanage.rite_request() resolves the day's tag sets with daily_tagger
     (vesperal for Vespers, Compline, and grace before supper) and selects the
     primary and alternates.
  4. Corpus.compose() recursively searches tagged content and returns a Rite.
  5. The translation, chant, and header corpora are superimposed on that Rite.
  6. renderer.render_rite() renders the Rite to HTML, which the store sets as the
     rite signal; pray-view.js writes it into <main>.
  #+END_EXAMPLE

  Loading a rite URL directly follows steps 2 to 6 inside =pray.tpl=, which writes
  the HTML into the page before any script runs.

* Testing

  - Python tests run with =pytest=: =test_breviarium.py= compares composed rites
    against golden output, =test_data_content.py= checks the data files,
    =test_ordo.py= covers =datamanage.ordo()=, and =kalendar/= has its own
    kalendar, daily-tagger, and Easter tests.
  - Frontend tests run with =npm test= (=node --test frontend/tests/=) and cover
    routing, the pray store's pure functions, the ordo panel, and chant.

* Infrastructure

  =flake.nix=, =flake.lock=, =package.json=, =package-lock.json=,
  =pyproject.toml=, and =uv.lock= remain at the repository root because they
  describe the complete source, frontend, and Python workspace. Root =.envrc= and
  =.python-version= provide project-level tool discovery.

  Deployment modules and provider policy files live under =nix/=. The flake passes
  its tracked source, the =buildNpmPackage=-generated frontend bundles, and the
  flake-pinned chant books to =nix/nixos-config.nix= for installation under
  =/var/lib/libu=. The development shell provides Node.js, copies the generated
  bundles into =web/resources/dist=, and merges the same flake-pinned chant books
  into =data/generated/liber-usualis-chant= and =data/generated/fcc=.
  Deployment preserves an operator-provided =books.json= and any generated books
  other than those two trees while replacing the tracked application and the
  pinned chant books.

  =nix/image-formats.nix= customizes nixpkgs' native image variants. The
  =libu-images= NixOS configuration exposes Linode, Proxmox, Amazon, application
  ISO, and installer ISO images through =system.build.images= and
  =nixos-rebuild build-image=. Package aliases preserve the corresponding
  =nix build .#libu-*= commands. Docker output is not provided. The separate Linode
  hardware module backs the installed host's =nixos-rebuild= configuration and is
  not included in generated images because its filesystem UUIDs are host-specific.
